# pull-request

## 前提

- 対象は `master` をデフォルトブランチとする GitHub リポジトリ（`~/dotfiles` 想定）
- マージ方式は **merge commit**（履歴が `Merge pull request #N from lil-shimon/<branch>` で揃っている）
- `deleteBranchOnMerge: true` — マージ後にリモートブランチは自動で消える。ローカルは残る
- `gh` は認証済み

## 手順

### 1. 現状を把握する

```bash
git status --short
git branch --show-current
git diff
git diff --staged
```

- **差分が無ければここで止める**。何も無いのにブランチを切らない
- すでに staged / commit 済みのものがあるかを先に確認する（二重コミットを避ける）
- 変更が複数の文脈にまたがっていないかをここで見積もる（手順 3 のコミット分割に効く）
- **`git branch --show-current` は commit のたびに打つ。手順の最初に1回ではない。**
  同じワーキングツリーを別セッションが共有していると、コミットの合間にブランチが
  切り替わっていることがある

### 2. ブランチを用意する

`master` に居るなら **必ず切る**。master へ直接コミットしない。

```bash
git switch -c <type>/<kebab-case-summary>
```

`<type>` はこのリポジトリの実績順に `feat` / `chore` / `refactor` / `docs` / `fix`。

- `feat` — 設定・ツール・スキルの新規追加
- `chore` — 既存設定の調整、依存やバージョンの追随
- `refactor` — 挙動を変えない整理
- `docs` — ドキュメントのみ
- `fix` — 壊れているものの修正

すでにトピックブランチに居て、その名前が今回の変更内容と一致しているならそのまま使う。
**一致していなければ切り直す**（`chore/foo` のブランチに無関係な `feat` を積まない）。

### 3. commit する

**1コミット = 1つの文脈。** 実装とテスト、設定変更とドキュメント更新は目的が違うので分ける。
後からレビューで読んだときに、差分の意図が1つに絞れる粒度に保つ。

```bash
git branch --show-current
git add <同じ文脈のファイルだけ>
git commit
```

**`git add` の前に毎回ブランチを確認する。**
2コミット目以降でこれを飛ばすと、別セッションが切り替えたブランチの上に積んでしまう。

- 複数ファイルを1コミットに含めてよい。ただし文脈が同じものに限る
- 分けたコミットが残っている間は手順を繰り返す（`git status` が空になるまで）

メッセージは **サマリが英語、本文が日本語**。

```
show the prompt in the herdr agent sidebar rows

既定の「スペース名 + エージェント種別」では、どのペインで何を走らせているかが
サイドバーから読み取れない。トークンを差し替えて、1行目にプロンプト先頭が
来るようにした。

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

- **サマリは英語・小文字始まりの命令形**。`feat:` のような prefix は付けない（type はブランチ名が持っている）
- **本文は日本語で Why だけを書く。** 何を変えたか（What）とどう変えたか（How）は
  差分を読めば分かるので書かない。書くのは「なぜその判断に至ったか」だけ
- 1行が長くなりすぎない位置で折り返す
- `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>` を末尾に入れる
- Why が自明な変更なら本文は省いてよい

`#62` 以前のコミットは本文も英語だが、**そちらには揃えない**。
読み返す速度を優先して日本語に寄せる。サマリだけ英語なのは、
ログを1行で流し読みする時に `git log --oneline` が横に伸びないため。

### 4. push して PR を作る

```bash
git push -u origin <branch>
gh pr create --base master --title "<title>" --body "$(cat <<'EOF'
...
EOF
)"
```

タイトルはコミットのサマリをそのまま使ってよい。日本語タイトルも実績がある
（手順そのものが主題の PR など、英語サマリだと意図が落ちる場合）。

**本文は日本語。** 既存 PR の構成に揃える。

```markdown
## What

何を変えたか。差分の要約ではなく、変更の単位ごとに1行。

## Why

なぜその判断をしたか。採らなかった選択肢がある場合は表で並べて理由を書く。

## 動作確認

**実際に叩いたコマンドとその出力を貼る。** 「確認しました」だけは書かない。

## Note / 対象外

引っかかりうる副作用、スコープから外したもの。

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

- 見出しは変更の性質に合わせて増減してよい（`## 概要` `## 変更内容` `## 選択肢と判断` `## 影響しない範囲` などの実績がある）
- **`## 動作確認` は必須**。設定ファイルなら構文チェック（`luac -p` / `sh -n` / `bash -n`）、
  バイナリなら `--version` の実測、サーバなら reload の戻り値、と「叩いた証拠」を必ず1つ以上入れる
- 関連 Issue があれば `Refs #59` を入れる

### 5. マージするかを判定する

**次の条件に1つでも当たればマージしない。** 当たらなければ手順 6 でそのままマージする。

- 既存の挙動が変わり、**目で見ないと確認できない**（配色、キーバインド、UI レイアウト、通知）
- 既存の設定やデータを**壊しうる / 戻すのにコストがかかる**（削除、リネーム、移行、バージョンの載せ替え）
- PR 本文の `## 動作確認` に、**実測できずに残した検証項目**がある。
  ただし**マージ後にしか確認できない項目は数えない**。
  マージしないと実測できないものを「未実測だから」と保留の理由にするのは循環になる
- 複数案から選んだ結果で、その選択が**本人にしか判断できない**（好み・運用方針が絡む）
- ユーザーが明示的に「マージするな」「確認したい」と言っている

迷ったら**マージしない側に倒す**。マージは後から打てるが、取り消しは履歴を汚す。

### 6. マージする（既定）

```bash
gh pr merge <N> --merge
git switch master && git pull
git branch -d <branch>
```

- `--merge` を使う。`--squash` / `--rebase` はこのリポジトリの履歴の形と合わない
- リモートブランチは `deleteBranchOnMerge` で自動的に消える。**ローカルは自分で消す**
- CI がある場合は `gh pr checks <N>` がグリーンになってからマージする

### 7. マージを保留する

```bash
gh pr edit <N> --add-assignee lil-shimon
gh pr comment <N> --body "..."
```

**`gh pr edit --add-reviewer lil-shimon` は使えない。**
GitHub は PR 作者本人にレビューリクエストを出せず、
`Review cannot be requested from pull request author` で失敗する。
このリポジトリの PR は全部 lil-shimon 名義なので、この経路は常に閉じている。
代わりに assignee + コメントで「本人の確認待ち」を表現する。

コメントには**何をどう確認してほしいかを操作手順で書く**。「動作確認お願いします」は書かない。

```markdown
## 確認してほしいこと

マージ前に目で見ておきたい項目。

1. `wezterm` を再起動して、タブバーの配色が Tokyo Night になっていること
2. `Ctrl+Shift+p` が効かなくなっていること（トグルを削除したため）
3. `Ctrl+Shift+o` の透明度トグルは従来どおり効くこと

問題なければ `gh pr merge <N> --merge` で。
```

最後にユーザーへ **PR の URL と、保留した理由・確認項目**を提示する。
マージまで済ませた場合との差が伝わるように、「マージしていない」ことを明示する。

## メモ

- ブランチを切らずに master へコミットしてしまった場合は、
  `git switch -c <type>/<name>` でブランチを作り直し、
  `git switch master && git reset --hard origin/master` で master を戻す
- PR 作成後に追加の指摘対応をした場合、同じブランチに push すれば PR に反映される。
  PR 本文の `## 動作確認` も追随させる（古い実測値を残さない）
- コミットを分けたのに PR にまとめると、レビュー時に分割の意図が失われる。
  文脈が本当に独立しているなら **PR ごと分ける**ことを検討する
